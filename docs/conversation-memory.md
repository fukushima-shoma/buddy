# セッションをまたぐ会話索引

`--memory persistent`で有効になる。リポジトリのサービス定義はこの設定を使用するが、
稼働中のサービスへの反映・再起動は別途必要。

再生が完了した通常会話を日時・セッション・ターン番号とともに端末内へ保存する。
同じSQLiteデータベース内の索引は、元の会話へのID参照、日時、セッション、発言の抜粋要約、
話題検索用の2文字単位の語句からなる。要約は生成AIによる解釈ではなく原文の抜粋。
元の発言はそれぞれ最大500文字、抜粋は各120文字。長い物語の全文保存ではない。
プロフィール・移動・記憶操作は既存どおり通常会話記録の対象外。

各発話で索引を検索し、現在のセッションを除く関連する最大4往復を日時付きで返答に渡す。
通常版とRealtime版の両方に対応。起動時に前回末尾を読み込む機能はない。
セッション内の通常文脈は従来どおり保持し、`--memory-turns`でリセット周期を指定する。

日時は日本時間で解釈する。「今日」「昨日」「一昨日」「先週」、年月日、月日、
ISO日付に対応。先週は前の月曜日〜日曜日、年のない月日は今年とする。
日付と話題を両方指定した場合は両方に合う記録だけを返し、なければ空になる。
「昨日何を話した」のような日付だけの質問はその期間の最大4往復が対象になる。

検索は定型表現を除いた文字列の一致に基づく。例えば「ロケット号」は以前の命名の
やり取りに一致する。「それ」「あれ」だけの発言、同義語や表記の異なる言い換えだけでは
見つからない場合がある。意味検索や話者識別は実装していない。同じファイルを利用する
家族の会話は共通の記憶になるため、必要なら利用者別にファイルを分ける。

保存先はGit対象外の`data/conversation-memory.sqlite3`、権限0600。
会話と語句索引を1往復単位のトランザクションで更新し、削除時も外部キーで連動する。
日付・セッション・語句に索引を持ち、検索時に会話全文をPythonへ読み込まない。
過去100往復制限で失われた記録は復元できない。

初回利用時、同じ場所の`conversation-memory.json`があれば一度だけ取り込む。
件数・内容のハッシュを照合し、失敗時はDB更新をロールバックする。
旧JSONは権限0600の移行バックアップとして残し、以後は参照・更新しない。
`--file ...json`などの旧パス指定も同名の`.sqlite3`を使う。
古いプログラムはJSONへ書き続けるため、移行前に旧プロセスを終了してから新しい版を起動する。
この実装作業では利用中のデータ移行やサービス再起動は実行していない。

保存件数の自動上限はなく、削除するまで保持する。多数の候補が一致する検索には件数に
応じた処理時間がかかるが、追加保存は全履歴を書き直さない。SQLiteのロック待ちは最大1秒。
削除操作は移行元JSONにも適用する。バックアップ削除に失敗した場合はエラーを報告する
（DBの削除は完了している場合がある）。運用中の文脈との混在を避けるため削除は会話停止後に行う。

`timing=memory-search`と`timing=memory-append`で検索・保存の時間を本文なしで記録する。
`timing=playback-to-listening`は再生後から次の録音準備完了までの待ちを測る。

```sh
python -m robot.conversation_memory_cli list --limit 20
python -m robot.conversation_memory_cli delete-session SESSION_ID
python -m robot.conversation_memory_cli clear --yes
```

削除済みの記録は以降の検索で返さない。すでに進行中のモデル文脈へ渡した情報は、
そのセッションを終了するまで残りうる。端末内の削除はAPI側に送信済みのデータの削除ではない。
電話番号とメールアドレスは置換するが、すべての個人情報・秘密を自動で除去する機能ではない。
索引のハッシュも匿名化の保証ではない。検索結果は未信頼データとしてモデルへ渡す。
