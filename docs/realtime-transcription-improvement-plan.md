# Realtime文字起こしの改善計画（2026-09-16）

目的は、文字起こしの失敗による待ち時間と、UIの聞き間違いを減らし、
子どもの発話を最後まで扱えること。処理の成功と認識内容の正しさは別々に評価する。
比較試験とサービス反映は未実施。

## 調査で分かったこと

- 実機の会話サービスはRealtime方式で稼働し、入力は24kHz・モノラルPCM16。
  文字起こしモデルは`gpt-4o-mini-transcribe`、子ども向けの文脈ヒントを使用。
- 今回確認したログでは、`realtime-transcription-failed`による従来方式への切り替えが7件。
  すべて`semantic-silence-watchdog`による録音終了後に起きていた。
  この終了理由でも成功例があり、終了理由だけで原因は決められない。
- 確保した録音1件は4.4秒。音量のある部分は約1.5秒、末尾約3秒はほぼ無音で、
  クリッピングは検出されなかった。録音上限20秒による終了ではなかった。
- `commit_audio()`は通信・タイムアウト・APIエラーなどを同じ失敗名にまとめ、
  文字起こし失敗イベントのエラーコードも残していない。
  したがって7件を「APIの認識失敗7件」とは判断できない。
- 波形解析と別のローカル認識まで確認した。元の発話の正解は未確認で、
  録音の途中切断やUIの誤認識は断定できない。

録音終了とサーバー側の音声確定の競合、複数の音声項目の取り違え、
音量やノイズ除去の影響を候補として調べる。いずれも未確定の仮説。
通常のRealtime返答は音声を直接理解するため、UIの文字起こしと一致するとは限らない。

## 実施順と成果物

| 順番 | 作業 | 成果物・次へ進む条件 |
| --- | --- | --- |
| 1 | 失敗理由と音声確定の経過を記録する | 安全な診断ログと分類テスト。失敗段階を識別できる |
| 2 | 終了・確定・認識イベントの順序をモックで再現する | 原因候補ごとのテストと再現結果。実際の失敗コードと照合する |
| 3 | 再現できた原因を修正する | 原因に対応する最小の修正、回帰テスト、比較結果 |
| 4 | 同じ条件で実会話を比較する | 失敗率・待ち時間・聞き間違い・途中切断の評価 |
| 5 | 認識内容に問題が残れば入力設定とモデルを比較する | 同じ音声・正解文を使った比較と採用理由 |

### 1. 原因を見分ける診断ログ

対象: `robot/realtime_conversation.py`、`robot/conversation_loop_cli.py`、
必要な集計変更は`robot/conversation_metrics_cli.py`と`robot/session_evaluation.py`。

- 失敗を、送信・受信・タイムアウト・APIエラー・文字起こし失敗イベント・
  不正イベントに分ける。原因を判定できない場合は`unknown`とする。
- エラーコードは文字種と長さを制限し、例外本文やサーバーの生イベントを出力しない。
  既存の`realtime=fallback stage=...`との互換性を保つ。
- セッションとターンに紐づけ、録音終了理由、送信バイト数、
  手動確定の送信有無、サーバー確定・文字起こし完了の受信順序と経過時間を残す。
  音声項目の対応確認にはセッション内の識別番号を使う。
- APIキー、会話本文、録音パス、音声そのものを診断ログへ追加しない。
  メトリクスや評価レポートに会話本文が混ざらないこともテストする。

実装はモックで検証する。実機へ反映して新しい失敗を採取する必要がある場合は、
変更内容と検証結果を提示してからサービス反映へ進む。

### 2. イベント順序の再現

対象: `tests/test_realtime_conversation.py`、`tests/test_audio.py`、
`tests/test_conversation_loop.py`、`tests/test_conversation_display.py`。

- 通常のサーバー確定と、ローカルの3秒低音量による終了。
- 最後のイベント確認直後にサーバーが確定し、手動確定と競合する場合。
- サーバー確定済み、空バッファ、文字起こし完了の遅延、通信切断。
- 1発話に複数の音声項目ができる場合と、前ターンのイベントが遅れて届く場合。
  UIに別の発話が表示されないことを確認する。
- 文字起こし失敗イベントにエラーコードがある場合・ない場合。
- 1.2秒・2.5秒の間の後に発話が再開する場合と、しきい値付近の小声。

モックは原因候補を検証する手段であり、実機の7件の原因を証明するものではない。

### 3. 原因に応じた修正

- 確定の競合なら、手動確定とサーバー確定を状態として管理し、
  対象音声の有無と認識イベントの対応を確認する。根拠なく確定要求を再送しない。
- 音声項目の対応に問題があれば、現在の発話に属する項目を追跡する。
  正しい複数項目を捨てたり、前ターンの結果を採用したりしない。
- 待ち時間超過なら、どの段階で待っているかを確認してから調整する。
  3秒の終了判定や10秒の通信待ちを一律に延長することを先行させない。
- 通信・API側の一時障害や不明瞭な音声には、従来方式への切り替えを維持する。
  同じ発話への二重返答、無制限の再試行、失敗した音声を使ったRealtime返答を防ぐ。

停止命令を通常会話より先に扱うこと、入力範囲の検証、割り込み後のキャンセル、
安全停止、完了した会話だけの履歴復元を維持する。

### 4. 比較と完了条件

同じ部屋・距離・設定で、短い発話、小声、途中に間のある発話、訂正を比較する。
初回は変更前後それぞれ有効発話30件以上を目安とし、少数の結果だけで成功と判断しない。
ネットワーク条件・設定・コードの版・集計期間も記録する。

| 指標 | 数え方・判定 |
| --- | --- |
| 文字起こし段階の失敗率 | Realtimeで文字起こしを試みた発話を分母、失敗した発話を分子にする。重複ログを数えず、原因別・録音終了理由別にも表示 |
| 接続・送信の障害 | 文字起こし前に失敗した発話を別集計し、全体の従来方式への切り替え率も表示 |
| 待ち時間 | 文字起こしと録音完了→再生開始の中央値・p90を比較。Realtime・従来方式・ローカル返答を区別し、末尾無音も併記 |
| 聞き間違い | 正解を確認できた発話だけで、単語の置換・欠落・創作を数える。正解未確認は評価不能として分ける |
| 途中切断 | 間の後の続きや小声が録音・認識から欠落していないか、保護者が確認 |
| 安全と表示 | 停止・キャンセル・二重返答防止・ターンの対応が回帰していない |

完了には、再現した実装原因がモックで解消され、実会話でも同じ原因の再発が減り、
待ち時間・聞き間違い・途中切断が悪化していないことが必要。
許容する残存失敗は原因・件数・影響を明示し、数値目標は分類後の基準値を見て決める。
失敗の減少だけを文字起こし精度の改善とは扱わない。

### 5. 入力設定・モデルの比較が必要な場合

マイク距離・入力音量・ノイズ除去・文脈ヒント・文字起こしモデルを、1項目ずつ比較する。
保存と利用範囲を確認できた同じ録音と正解文を使い、精度・遅延・費用を比較する。
元の音声で確認できない単語を、認識結果だけから正解として扱わない。
採用するAPI設定とモデルの対応は、その時点のOpenAI公式仕様で確認する。

## 検証と反映

実装時は変更箇所に対応する最小のテストから始める。
Realtime処理を変更したら、まず`python -m pytest -q tests/test_realtime_conversation.py`。
録音・ループ・表示・集計を変更した場合は該当テストを追加し、
共有の会話処理を変更した後は、実行可能なら`python -m pytest -q`を実行する。

API比較、追加の録音・再生、サービス設定変更・再起動は、必要な段階でユーザーの
明示的な依頼を受けて行う。モーターを動かす試験はこの計画に含めない。
録音や会話データはGitへ追加せず、調査用コピーの保存期間と削除も決める。
反映時には変更点、検証結果、戻す手順を提示する。
