# 会話応答速度の改善：採用方針と比較計画

作成日: 2026-11-07

状態: 段階1の実装方針は承認済み。固定音声キャッシュとチャンク設定を実装した。
準備・利用手順は[固定音声キャッシュ](fixed-speech-cache.md)を参照。
2026-11-08: 固定音声39件の実API生成とサービスへの有効化を完了。
全39件のキャッシュ読込と起動ログでの有効化を確認。チャンクサイズは16KiBを維持。
音声機器を使う品質確認とA/B比較は未実施。

## 現状と目的

通常会話はRealtimeによる録音中の送信・音声の逐次再生を導入済み。
文字起こし確定後に停止・記憶等の操作を判定し、通常返答を要求する。
従来方式は返答全文を生成してからTTSへ渡し、音声を16KiB単位で受け取る。
従来のTTSキャッシュはプロセス内だけなので、再起動すると消える。
今回追加した固定音声キャッシュは明示的に有効化した場合だけ読み込む。

既存の集計は経路別の中央値・p90・p95・最大値と、末尾低音量を加えた
推定応答時間に対応している。スピーカーからの実発音は測っていない。
また従来方式のstreaming計測はplayer呼び出し前、Realtimeは最初の書き込み前で、
経路間の計測位置に差がある。比較時はこの差も記録する。

目的は最初の意味のある返答が聞こえるまでの短縮。
録音の途中切断、誤返答、音切れ、停止操作の遅延を増やさない。
体感のための相づちだけを先に再生して改善とは数えない。

## 段階1：先に取り込む実装

### 固定フレーズ専用の永続音声キャッシュ

- 既存の固定文から、挨拶・聞き返し・終了・移動確認/停止確認を明示的に登録する。
  `LOCAL_SHORT_REPLIES`、聞き返し定数、操作返答定数を参照し、文言の二重管理を避ける。
- 自由会話、プロフィール、共有体験、名前を埋め込んだ文は登録しない。
  一般のTTSキャッシュをそのままディスクへ保存する実装にはしない。
- 専用の準備CLIで固定音声を事前生成できるようにする。
  通常起動時にまとめて生成する処理は入れない。生成対象数と設定を確認できるようにする。
  CLIの既定はモック、再生は行わない。モック出力を本物のキャッシュとして扱わない。
- モデル・声・速度・読み上げ指示・本文・形式・キャッシュ形式版をキーに含める。
  設定や文言が変わると古い音声は一致しない。API内部の声の変化に備え、明示的な再生成も可能にする。
- 保存先はGit対象外の`captures/audio/fixed-speech-cache/`。
  一時ファイルからの置換、音声形式と内容の整合性チェック、ファイルサイズ上限を設ける。
  欠損・破損・読取不可では通常の音声合成へ戻り、会話を止めない。
- 会話CLIで利用を明示的に有効化する。既定では無効。
  準備CLIが生成した音声だけを読み取り、実会話中は永続キャッシュを増やさない。
- 音声があっても操作判定を省かない。特に停止実行後に停止確認を再生する順序を維持する。
- 再起動後のキャッシュ一致時にTTS API呼び出しがゼロになることをモックで確認する。
  設定変更、許可されていない文、破損、書き込み失敗、通常生成への復帰も検証する。

対象: `robot/speech.py`、固定フレーズ定義、準備CLI、
`robot/speech_cli.py`のfactory、`robot/conversation_loop_cli.py`と対応テスト。
専用モジュールへの切り出しは依存関係を見て決める。

構造として採用できるが、実際の音声素材は再生確認後に運用へ入れる。
初回のAPI費用・保存容量は準備した固定フレーズ数に比例する。今回の承認対象は
コードとモック検証までで、実API生成とサービスへの有効化は別途実行する。

### 比較用のチャンクサイズ指定

- TTSの読み出しを16/4/2KiBから指定可能にする。既定は16KiBのまま。
- 不正値は拒否する。会話CLIと生成CLIから同じ設定を渡せるようにする。
- チャンク境界が変わっても音声の全バイトが欠落・重複しないこと、
  中断時に未完了音声をキャッシュしないことをモックで検証する。
- 実験時の設定・キャッシュ有無を計測値とともに記録できるようにする。

## 段階2：比較してから採否を決める改善

以下の数値は今回提案する実験上の目安であり、資料から得た性能保証ではない。

| 実験 | A / B | 観測するもの | 採用の条件 |
| --- | --- | --- | --- |
| 固定音声 | キャッシュなし / 事前生成済み | 新しいプロセスでのAPI呼出回数、開始待ち、音声の適合 | 対象文のAPI呼出ゼロ、声と内容が正しい、通常生成への復帰が成功 |
| チャンク | 16KiB / 4KiB / 2KiB | 最初の受信・書込・音声開始、CPU、音切れ、再生完了 | 中央値で100ms以上または10%以上短縮し、p95と音切れが悪化しない |
| 終了判定 | medium / high（lowは必要時の参照） | 末尾待ち、途中切断、聞き直し、watchdog、入力失敗 | 推定待ち中央値200ms以上短縮、途中切断・聞き直し・失敗を増やさない |
| 代替経路の逐次化 | 全文完成後TTS / 最初の一文からTTS | 短文/物語別の開始待ち、文間の間、抑揚、API回数 | 対象経路の中央値20%以上短縮、読み飛ばし・二重再生なし、音質と費用が許容範囲 |
| 先読み生成 | 操作判定後生成 / 判定と並行生成・再生は保留 | 確定→生成/再生、破棄率、追加費用、文脈整合性 | 通常会話の中央値200ms以上短縮、p95非悪化、誤再生・操作先行・破棄音声の履歴混入ゼロ |

### 共通の比較手順

1. モックで失敗・中断を含む機能検証を行ってから、実APIの比較へ進む。
2. 実API比較は合成した日本語音声/固定テキストを利用し、個人の会話データは使わない。
   モデル、声、速度、指示、履歴、端末、回線を揃え、一度に一つの変数だけ変える。
3. 同じ入力を各条件へ渡し、A/Bの順番は交互または無作為にする。
   初回接続/接続済みとキャッシュ有/無を別々に扱う。
4. まず各条件30試行程度で傾向を見る。最終候補は各条件100試行以上を目安に再比較する。
   同一入力の差分と件数・中央値・p95・最大値を出す。少数試行のp95は不安定であり、
   閾値付近なら採用を断定せず追加試行する。
5. 通信失敗やフォールバックを除いて好成績だけを作らず、成功時の分布と失敗率を併記する。
   Realtime/従来方式/ローカル/操作を分ける。従来方式を直接選んだ試験と障害後の代替も分ける。
6. 有望な候補だけ同じ部屋・距離・音量で実機比較する。
   発話末尾から実発音までの測定は、同じ時間軸に入力と出力が残る別途承認した記録で行う。
   合成音声の最初の非無音サンプル検出と、スピーカーの実発音は別の測定として扱う。
7. 設定で元に戻せる形にし、検証を通った項目だけサービスへ反映する。

### 実験ごとの注意点

- チャンク比較: キャッシュを無効にし、24kHz/16bit/monoなら16KiBは約341ms分の
  音声データに相当する。ただし生成速度と通信バーストがあるため341msの遅延とは限らない。
  Pythonのパイプバッファも介在するので、チャンクだけ変更して効果がなければ
  flush/バッファ方式を別実験にする。先頭無音の自動切除は今回採用しない。
- 終了判定: 短い完結文、1.2秒/2.5秒の途中の間、言い直し、小声、背景音を含める。
  3秒watchdogは固定し、同時に変更しない。子どもの自然発話での確認は合成試験の後に行う。
- 逐次化: 句点単位から試す。略記・引用・長く句点が来ない文の扱いを決める。
  文章を全部完成させる時間と話し始める時間を混同しない。
  API失敗、割り込み、文境界での中断、記憶へ保存する範囲をモックで確認する。
- 先読み: Realtimeの音声入力確定後、文字起こし・操作判定待ちとの重複から検討する。
  API上でのイベント多重受信、キャンセル、会話項目管理を設計してから試作する。
  出力は上限付きで保留し、操作判定が終わるまで再生しない。
  記憶検索結果や物語モードが変われば破棄する。移動・保存等の副作用は先行しない。
  不採用の生成を会話履歴に残さない。高い破棄率なら対象を短い通常会話へ限定する。

## 実施順序と完了条件

1. 段階1の実装方針を確認後、固定音声キャッシュとチャンク設定を実装・モック検証。
2. API利用を伴う固定音声の準備とチャンク比較を実施。
3. 音声機器の電源を入れた状態で固定音声・再生品質・終了判定を評価。
4. 代替経路が依然として問題なら逐次化を試作し比較。
5. 通常会話に文字起こし待ちが大きく残る場合だけ先読みを試作する。

実装の検証は`python -m pytest`で対象テストから開始し、共有処理変更後に全体テスト。
実API成功、モック成功、実機成功を別々に報告する。
音声デバイスがオフでも段階1を完了できる。サービス再起動や実機試験は含めない。
